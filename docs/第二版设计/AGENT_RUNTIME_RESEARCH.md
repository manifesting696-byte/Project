# Agent 运行时与模型 Provider 分离：一手资料摘录

调研日期：2026-11-06。以下以框架维护者的仓库文档或源码为依据；[本项目的 `DeepSeek Harness.md`](DeepSeek%20Harness.md) 是审计设计要求，不作为 DeepSeek 项目的实现证据。

## 可借鉴的架构事实

| [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness/blob/master/README.md) | 它确实是 DeepSeek AI 发布的 TypeScript Harness，当前 README 标为 developer preview。`agent` 包声明公共 Agent 接口与 registry，`agent-loop` 包提供默认驱动；扩展依赖前者，不直接依赖具体 loop。[架构](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)、[Core](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/core.md) | `llm` 定义消息、请求、流与 adapter seam；具体 adapter 按 provider route 注册。添加 adapter 不要求修改 agent loop。[LLM adapter 指南](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cookbook/adding-an-llm-adapter.md) | `tools` registry 持有定义并负责受控执行；loop 经 registry 派发。工具调用有 pre/execute/post 扩展点及最终结果记录。[工具定义](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/tools.md)、[执行链](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/tool-execution-pipeline.md) |

DeepSeek 的“Capability Seam”有 **Service Definition、Service Provider、Consumer** 三个角色；其文档明确说只有一个角色并不构成可替换能力。这个原则可借鉴，但其 Cordis、事件瀑布与热卸载机制是 TypeScript 产品的具体选择，不能直接推导为本 Python 服务必须实现同样的插件运行时。[架构原文](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md#capability-seams)

## 对本项目的落点

目前代码已出现轻量分层：`agents/base.py` 的 `ModelAgent` / `SpecialistAgent` / `ArtifactAgent` 复用调用及产物校验，具体 Semantic、Query、Analysis、Presentation agent 持有角色差异；`core/model.py` 的 `ModelRunner` 协议与 `ModelClient` 管理消息、工具循环和 Pydantic 输出；`core/transport.py` 的 `ChatTransport` 与 `OpenAICompatibleTransport` 封装 HTTP Chat Completions；`application/service.py` 注入模型并组合 Agent。参见本项目 [Agent 基类](../src/enterprise_agent/agents/base.py)、[模型循环](../src/enterprise_agent/core/model.py)、[传输适配器](../src/enterprise_agent/core/transport.py)、[应用组合](../src/enterprise_agent/application/service.py)。这些是 2026-11-06 阅读时的状态，代码继续变动时应以实际源码为准。

1. **保留窄契约，避免继承树继续增长。** Agent 基类只承载共享执行与产物不变量；角色 prompt、工具清单、输入校验留在具体 Agent。AutoGen 证明抽象基类可行，LangGraph 与 OpenAI SDK 则说明函数/组合也可行；两者都不支持“每种角色都需一个深层父类”的结论。
2. **把模型调用与厂商协议分开。** `ModelRunner.run(...)` 是业务 Agent 的消费端；模型循环决定回合上限、工具调用、结构化输出和事件；`ChatTransport.complete(...)` 只翻译请求/响应。切换 DeepSeek、OpenAI、Qwen 时先验证它们在所选 endpoint 上的 JSON 输出、工具调用、错误语义和限额差异；共同兼容的才复用 `OpenAICompatibleTransport`，差异显著时新增 adapter。DeepSeek 的 adapter 指南明确要求不支持的能力报错而非静默忽略。[指南](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cookbook/adding-an-llm-adapter.md)
3. **工具授权属于可信执行层。** 角色只收到白名单工具；运行时对返回的工具名称再次校验。SQL 只读、语义绑定、产物引用等业务授权保留在现有 toolbox/gateway/存储边界，不交给模型或 transport 决定。DeepSeek 的 registry 和执行链同样区分模型可见 schema、执行逻辑与 policy。[工具定义](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/tools.md)
4. **暂不引入通用插件管理器。** 目前可替换点集中在模型传输和少数角色/工具组合。先用显式构造注入和配置选择验证替换价值；只有需要动态发现、独立生命周期或多实现共存时再加入 registry。DeepSeek 的 profile/bundle 机制服务于其完整产品组合，不是小型 Python 应用的必要前提。[架构原文](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md#profiles-and-bundles)

最小验证：用假 `ChatTransport` 驱动同一 `ModelClient` 的普通输出、工具调用、无授权工具、无效 JSON 重试和轮次上限；再以同一 `ModelRunner` 替换 Agent 的模型实现，确认角色源码无需修改。对真实 provider 另做少量协议契约测试；不能仅凭接口形状宣称完全可替换。
