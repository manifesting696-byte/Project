### 2. 用两分钟介绍你的企业问析项目

**参考回答**

这个项目面向企业数据库上的问答和分析。用户可以问有哪些表、指标如何定义，也可以要求查询、统计、绘图或生成报告，并在后续对话里修改之前的工作。

整体上，Supervisor 先识别本轮有哪些独立要求，以及它们属于直接问答、新建工作还是修改已有工作。需要持久执行的要求会形成 Request，准备阶段合并完整要求并生成 Task 计划。SemanticAgent 处理业务语义绑定，QueryAgent 执行受限查询，AnalysisAgent 计算分析，PresentationAgent 生成展示产物。调度层按照依赖关系执行就绪任务。

真实结果统一保存为 Artifact，最终回答引用这些产物。需求修改时保存新的 Revision，并根据变化使相关任务及其下游失效。这样能够追踪用户要求、执行过程和最终数据的对应关系。

## 二、Agent 领域模型与意图识别

### 5. Request、RequestRevision、Task 和 Artifact 分别解决什么问题？

**参考回答**

Request 表示一项可以跨轮修改的业务工作，保存身份、状态和当前版本。RequestRevision 保存某次完整要求的不可覆盖快照。Task 表示专业 Agent 的执行节点，一项业务工作可以拆成多个执行节点。Artifact 保存实际生成的文字、表格、图表和报告，以及它们的来源。

例如“查询各产品平均产量并绘图”，可以是一项 Request，内部包含语义绑定、查询和绘图任务。下一轮修改统计年份时，Request 身份继续沿用，生成新的 Revision，并更新执行计划。

这些对象分别支持跨轮定位、历史审计、依赖调度和真实结果追溯。

### 6. 为什么需要 Revision？直接覆盖 Request 不行吗？

**参考回答**

覆盖会让历史任务失去当时的业务依据。用户先统计全部年份，之后改成 2025 年，如果只保存最新要求，就难以说明旧表格为什么包含其他年份。

Revision 保存当时完整的 description、parameters、inputs 和 outputs，并记录父版本及来源意图事件。Task 与 Artifact 关联具体 revision_id，因此能追溯产物对应哪次要求。Request 通过 current_revision_id 指向当前版本，调用方读取完整 Request 时可以拿到当前 spec。

版本快照也为变更比较和过时写入检测提供基础。

### 7. Intent 阶段到底输出什么？为什么后面还要准备阶段？

**参考回答**

Intent 输出 operations 和 clarifications。每项 operation 包含 request_id、action、category、instruction 和 refs，用于识别用户本轮提出的要求、修改目标及引用对象。

准备阶段再结合已有状态，把增量指令合并为完整 RequestSpec，同时生成初始 Task 计划。例如“改成 2025 年”在 Intent 中保留这次变化，在准备阶段补齐原来的统计对象、指标和交付要求。

这样每个阶段都有明确职责。完整 spec 和计划生成后还需要程序校验，再提交持久状态。

### 8. category 与 action 怎么区分？

**参考回答**

category 描述内容类别，当前有 general_qa、business_knowledge、data_analysis 和 result_interaction。action 描述本轮怎样处理工作，当前有 none、create_task 和 update_task。

项目现在明确规定，基础问答和企业知识使用 none，数据分析与结果交互使用 create_task 或 update_task，新增还是修改取决于是否改变已有 Request 的要求。这个关系在 Pydantic 校验器中也有约束。

create_task 这个名字容易与执行层 Task 混淆。它在意图协议中表达新建持久业务工作，后续才形成执行 Task。面试时我会把这层历史命名交代清楚。

### 9. “平均值是什么”和“项目中的可用库存是什么”怎么分类？

**参考回答**

我按回答所需的知识来源区分。平均值的数学定义属于 general_qa。项目中可用库存的业务口径需要查企业语义目录，属于 business_knowledge。

现存量、预留量这类词可能具有通用解释，也可能有企业特定定义。当用户询问当前系统中的字段含义时，应优先依据项目目录。意图上下文会提供数据库与能力概览，具体定义可以按需读取。目录无法确定业务口径时，需要说明缺失信息或澄清。

### 10. 如何处理一条消息中的多个需求？

**参考回答**

例如“解释平均值，再查询各产品平均产量”，会拆成基础问答和数据分析两项 operation。第一项可以直接回答，第二项需要建立持久工作。

拆分依据是用户能独立验收的业务要求。QueryAgent 查表和 PresentationAgent 绘图通常可以作为同一 Request 内部的执行节点。只有用户表达了独立业务要求时，才在意图层拆开。最终回答保留本轮原始要求的顺序，便于用户核对是否全部完成。

### 11. 如何判断“再画一张图”是新增还是修改？

**参考回答**

要同时判断交付要求和用户表达。“保留原来的图，再增加一张折线图”表达新增交付，可以建立新工作并引用历史数据。“把原来的柱状图改成折线图”表达修改已有工作的展示要求，需要定位原 Request 并生成新版本。

如果上下文中存在多张图，用户只说“改一下那个图”，应先定位指代。无法唯一确定时提出澄清，不能直接把最近一项工作当作目标。

### 12. Intent.refs 表达什么？为什么同时支持 Request 和 Artifact？

**参考回答**

refs 表达当前要求需要依据哪些已有内容或上游结果。kind 为 request 时，通过 id 和 output 引用某个 Request 的命名交付，适合同轮尚未执行完成的上游工作。kind 为 artifact 时，通过 id 精确引用已经存在的产物。

比如同轮“先统计，再绘图”，第二项可以引用第一项的命名表格输出。下一轮“解释上一张图”，可以直接引用那张图的 Artifact。实际执行时还会把业务引用绑定成明确的输入槽位，并验证资源属于当前会话和允许的范围。

### 13. 已有 artifact_id，为什么还需要 output 名称？

**参考回答**

output 是预期交付的逻辑名称，artifact_id 是一次实际产物的身份。例如上游承诺输出 supplier_table，下游在规划时可以先引用这个名字。上游执行后，再将 supplier_table 绑定到真实 Artifact。

重执行可能生成新 Artifact，逻辑交付名称仍然可以保持稳定。如果用户明确要求使用旧版本的数据，应绑定具体历史 Artifact。引用目标工作自己的旧结果时，也要使用历史 Artifact，避免形成自依赖。

### 14. 你如何保证模型输出结构正确？

**参考回答**

模型调用层使用结构化输出约束，并通过 Pydantic 做严格校验，包括必填字段、枚举值和额外字段限制。业务层继续检查 Request 是否存在、引用是否有效、依赖是否成环、输出名称是否重复，以及类别与动作是否匹配。

对于可修复的结构或业务错误，系统可以把具体错误交给模型修复，修复次数由程序限制。权限错误、版本冲突和上游等待有独立处理路径。结构合法之后，仍需要验证计划、执行结果和业务事实。

## 三、规划、调度与跨轮执行

### 15. 为什么用 Supervisor 加专业 Agent？

**参考回答**

Supervisor 负责意图、规划和协调，专业 Agent 负责语义、查询、分析与展示。每个角色拿到适合当前阶段的上下文和工具权限，能缩小选择范围，也便于分别评测。

这些角色可以共用模型服务，模型客户端统一处理传输与工具循环。这个架构会增加调用次数和调试链路，所以直接知识问答会走较短路径。是否值得拆成独立角色，需要结合任务复杂度和评测结果判断。

### 16. DAG 里有哪些字段？数据怎么传递？

**参考回答**

计划中的任务包含 task_id、objective、assigned_agent、depends_on、input_bindings、expected_outputs 和 params。depends_on 表示执行依赖，input_bindings 把上游结果绑定到当前任务的输入槽位。

执行后，任务通过 produced_outputs 把逻辑输出名映射到真实资源引用，计划的 output_bindings 再把任务输出映射到 Request 的交付。

例如查询节点输出 dataset，绘图节点通过输入绑定读取这个数据。程序需要同时验证执行依赖和数据引用，避免任务看起来已经就绪，实际输入却无法解析。

### 17. 同一轮多个 Request 是如何并行的？

**参考回答**

当前实现会统一调度本轮多个 Request 的执行 Task。调度器寻找依赖满足的就绪任务，在共享并发上限内分发执行，默认上限为 4。选择时在不同 Request 之间轮流取任务，避免一个大需求占满整个批次。

有依赖的节点等待上游完成，上游正在重规划时也需要等待。某项工作失败时，会处理它及其依赖方的状态，其他独立工作可以继续。结果完成顺序可能不同，最终响应仍按用户提出要求的顺序组织。

### 18. LangGraph 在项目里用了哪些地方？

**参考回答**

主要分三层。Turn 图组织 intent、prepare、commit、process 和 respond 等阶段。Request 图处理执行、验收、重规划、挂起和恢复。Task 图通过 Send 分发就绪任务。

LangGraph 承担状态流转和检查点能力，项目自己的 Request、Revision、Task 与 Artifact 继续表达业务状态。采用框架以后仍需要实现依赖校验、产物验收、事务、权限和幂等逻辑。

### 19. 动态重规划在什么时候触发？

**参考回答**

当执行结果揭示原计划需要调整时，例如语义绑定发现字段不可用、上游产物无法满足后续步骤，或者验收发现交付缺失，就可能触发重规划。计划中也有 replan_after，用来表达需要先执行某步再决定后续计划。

重规划需要依据真实反馈，更新计划版本，并明确保留、替换或取消哪些任务。可以复用的完成结果应保留。修改后的依赖关系和交付绑定还要重新校验，同时控制修复和重规划预算。

### 20. 用户改一个条件，怎么知道哪些任务需要重跑？

**参考回答**

准备阶段会比较新旧 spec 的描述、参数、输入和预期输出，再结合任务依赖处理失效。改变时间范围会影响查询结果，因此相关查询任务及其分析、展示下游需要重新执行。只修改图表样式时，可以复用原始表格，主要更新展示节点。

跨 Request 的依赖也要考虑。如果下游跟随上游当前命名输出，上游变化会影响它。如果下游绑定某个固定历史 Artifact，它引用的数据版本具有明确身份。复用判断必须包含输入版本、业务条件和产物来源。

### 21. 断电或者进程重启后，任务如何恢复？

**参考回答**

项目使用 PostgreSQL 保存业务状态，同时使用 LangGraph 的 PostgresSaver 保存执行检查点。检查点帮助恢复工作流现场，业务账本保存 Request、版本、任务、事件和产物记录。

恢复时需要读取已有执行状态，并利用 workflow_key 等幂等标识避免重复提交。Artifact 指纹结合内容、来源、SQL 和生产范围，支持同一次执行重放时识别已有结果。

涉及外部写操作时，还需要对应工具的幂等设计。检查点本身不能提供覆盖所有外部系统的 exactly-once 保证。

### 22. 两轮对话同时修改同一需求会怎样？

**参考回答**

项目用会话锁协调同一会话的 Turn，提交时还会核对预期 Revision 或版本，防止旧计划覆盖新状态。Revision、任务变更与相关事件尽量在同一事务中提交。

同轮内部允许多个 Task 并行，它们使用各自的数据库连接。并发执行仍要遵守依赖和资源作用域。遇到版本冲突应重新读取最新状态再处理，避免用过时上下文强行重试写入。

## 四、记忆、产物与数据可信度

### 23. 工作记忆和持久记忆分别保存什么？

**参考回答**

工作记忆是当前阶段需要的上下文视图，例如用户输入、候选 Request、相关产物概览、目录和执行反馈。持久记忆包括会话事件、摘要、Request、Revision、Task 和 Artifact。

当前初始上下文默认读取最近 24 条用户或回答事件、最近 12 项 Request、最近 16 项 Artifact 概览，以及摘要和目录信息。后续阶段再按自己的需要组装上下文，详情通过工具回读。

这些数量是当前配置值，还需要根据目标定位准确率、Token 和延迟做实验调整。

### 24. 摘要遗漏重要细节怎么办？

**参考回答**

摘要负责帮助定位历史工作，精确条件和结果保存在结构化对象与原始产物中。计算或回答具体数字前，应读取对应 RequestSpec、表格或 SQL，避免从摘要中恢复精确值。

摘要记录覆盖的事件范围，历史事件仍可回读。如果用户说“按之前那个口径”，系统要查到对应版本与定义。无法唯一定位时应澄清。评测中可以加入长历史里的条件修改、多个相似结果指代和摘要遗漏场景。

### 25. 你说减少 Token，减少了多少？

**参考回答**

目前能确认的是系统采用了概览加按需读取的上下文设计，已经核对的材料还不足以给出可靠的降幅。

我会用同一组长会话，对比全量历史注入与阶段上下文，记录输入 Token、总 Token、调用次数、响应时间和任务正确率。还要检查摘要调用与回读工具带来的额外消耗。只有在正确率可接受的条件下，Token 节省才具有解释价值。

### 26. 文字、SQL 查询结果、加工后的表格和图表怎么统一保存？

**参考回答**

Artifact 的 content_type 统一为 text、table、chart 和 report，同时通过 producer、payload、source_artifact_ids 以及 Request、Revision、Task 关联表达来源。

SQL 结果和二次加工表格都可以是 table，来源信息用于说明查询或加工过程。图表可以引用源数据 Artifact，报告可以关联它使用的表格、图表和文字。正文通过 content_ref 定位，元数据保存在数据库中。

最终 ResponseBlock 引用 Artifact，包括普通文字回答。直接问答生成的产物也有会话和轮次归属，允许没有执行任务关联。

### 27. 如何证明展示的图表数据来自真实查询？

**参考回答**

查询层生成数据 Artifact，保留 SQL 和来源信息。展示任务接收这个产物作为输入，生成图表并记录 source_artifact_ids。回答引用最终图表后，可以沿来源链回查数据表、查询及对应需求版本。

执行结果还要核对交付名称、类型和产物作用域，确认引用确实由允许的执行过程生成。测试中需要比较图表类别和数值与源数据是否一致。完整来源链能够支持检查，数值正确性仍需执行验收。

### 28. 企业语义层有什么用？为什么不直接生成 SQL？

**参考回答**

企业术语和数据库结构之间存在映射问题。同一个词可能对应不同指标，表关联也可能改变统计粒度。SemanticAgent 先确定表、字段、关系、指标、维度、时间范围和粒度，再交给查询阶段。

例如订单表与订单明细表关联后，直接累加订单金额可能重复计算。语义绑定和查询校验需要识别这个风险，必要时先按事实粒度预聚合。目录中尚未发布的候选指标，也需要先明确业务定义。

### 29. 怎样限制模型生成危险 SQL？

**参考回答**

项目使用 SQLGlot 解析 AST，限制为允许的查询类型，校验表、Schema、列、函数及关联关系。数据库层还使用只读账号，并结合超时、EXPLAIN 成本和行数限制控制查询。

工具执行由程序授权，模型提出的调用需要通过工具与参数校验。对于越权或不存在的数据源，系统应拒绝执行。业务正确性还需要检查聚合粒度、过滤条件和真实数据结果。

### 30. 为什么使用 PostgreSQL？数据库里保存了哪些内容？

## 六、RAG 简历岗位匹配项目

### 38. 介绍一下岗位推荐的完整链路

**参考回答**

系统先从简历提取学历、年龄、技能、项目经历和求职意向，形成用户画像。检索时先使用年龄和学历等标量条件过滤，在 job_full 集合中进行 Dense 与 BM25 混合召回，得到 Top 200 候选。

之后限定在这批 job_code 内，查询岗位要求与工作内容，进行多字段融合得到 Top 50，再使用 Cross-Encoder 对画像与岗位文本联合打分，结合规则得到最终 Top 10。

画像、摘要与近期对话通过 MySQL 保存和读取，支持后续调整城市、薪资等偏好。

### 39. 为什么 Dense 与 BM25 要一起用？

**参考回答**

Dense 有助于识别语义相近的经历和岗位要求，例如项目描述与岗位职责之间的相关性。BM25 对精确技能、框架名和岗位关键词有帮助，混合使用能覆盖两类匹配信号。

当前实现的 Dense 来自本地 BGE-M3，Sparse 由 Milvus 服务端的 BM25 Function 生成。融合方式与权重需要通过标注数据评估，并检查两条召回路径各自带来哪些有效候选。

### 40. 为什么分三个 Collection？为什么用级联检索？

**参考回答**

job_full、job_requirement 和 job_content 分别表示岗位整体、岗位要求和工作内容，便于把完整画像、技能和经历匹配到适合的字段。

级联先形成 Top 200 候选，再在候选范围内做其他字段匹配，可以控制后续检索与重排规模。代价是首轮漏掉的岗位难以在后续找回，所以需要单独评估候选集召回率。

候选通过 job_code 合并，字段缺失时保留岗位，并按可用字段调整融合权重。建人工标注池时可以合并多种召回来源，扩大对漏检岗位的检查范围。

### 41. 为什么还需要 Cross-Encoder？分数怎么融合？

**参考回答**

召回编码器适合预计算岗位向量与快速搜索。Cross-Encoder 联合读取画像和岗位文本，可以建模更细的匹配关系，但逐对计算成本更高，所以放在 Top 50 候选上。

当前默认多字段召回权重为整体 0.35、要求 0.40、内容 0.25，最终融合包含重排 0.60、召回 0.25、规则 0.15。它们是代码配置，需要通过验证集选择，现有证据不足以说明这些权重已经最优。还需要检查不同分数的尺度，并做单路检索、混合检索和增加重排的消融实验。

### 42. Metadata 过滤有哪些风险？

**参考回答**

硬过滤能排除明确不满足条件的岗位，也可能因为解析错误或字段缺失误删相关岗位。当前实现对缺失的年龄、学历等数值用负值表达未知，过滤时允许未知条件通过。

城市、薪资等偏好需要区分用户的硬要求与可协商偏好，还要统一薪资单位。评测时要查看过滤前后候选数和相关岗位保留率，定位画像抽取、数据清洗或过滤规则造成的损失。

### 43. Recall@10、MRR@10、nDCG@10 怎么计算？

**参考回答**

对一份简历，Recall@10 是前 10 个岗位中相关岗位数除以该简历全部相关岗位数，再按评测协议做汇总。它反映相关岗位被找回多少。

MRR@10 先找到前 10 名中的第一个相关岗位，记录排名倒数，未命中记 0，再对简历取平均。它关注首个相关岗位出现的位置。

nDCG@10 用相关性等级作为增益，并按排名折扣，再除以理想排序的 DCG。常用增益为 2 的相关性等级次方减 1，折扣分母为 log2(rank + 1)。它适合评价分级相关性的整体排序。

需要一起说明相关性标注规则、无相关岗位样本的处理方式和平均口径。

### 44. 你简历的 MRR 比 Recall 高，合理吗？300 份简历怎么标注的？

**参考回答**

多相关岗位场景下可能出现这种关系。例如某份简历有很多相关岗位，第一个结果就命中时倒数排名为 1，但前 10 个结果只覆盖部分相关岗位，Recall 仍可能较低。如果每份简历只有一个相关岗位，在相同样本与定义下应满足 MRR@10 不超过 Recall@10。

因此需要先给出相关性定义、标注范围和聚合方式，再解释简历中的三个数字。对于 300 份简历，我需要提供来源、标注说明、岗位候选池、数据划分和原始评测报告。

**证据状态**

简历记载 Recall@10 为 0.748、MRR@10 为 0.912、nDCG@10 为 0.836。当前已核对代码中找到人工标注候选池生成逻辑，尚未找到足以复现这三个数字的完整标注与结果文件。

### 45. 如果让你重新设计这套 RAG 评测，会怎么做？

**参考回答**

我会先冻结岗位快照和测试简历，再通过多路召回构建标注池，定义不相关、部分匹配和高度匹配等等级，并检查标注一致性。候选池覆盖有限时，需要说明相关性判断的范围。

调参集与最终测试集分离，相似简历和同一候选人的不同版本要避免跨集合泄漏。分别测首轮 Recall@200、进入重排前的候选召回率和最终排序指标，并比较 Dense、BM25、混合检索、多字段融合和重排的增益。

同时记录延迟、推理开销及按学历、城市、岗位类型划分的结果，判断提升来自哪些场景。

## 七、通用技术与个人经历追问

### 46. FastAPI 是异步的，为什么还可能堵塞？

**参考回答**

async 接口里如果直接执行同步模型请求、数据库驱动或长时间计算，仍可能阻塞事件循环。需要逐个检查调用链，使用合适的异步客户端，或者把同步 I/O 放到线程池，CPU 密集任务再考虑进程或独立服务。

Agent 请求还要限制并发、设置超时和传播取消信号。我会用请求耗时拆分与并发测试检查瓶颈。具体到当前项目，不能仅凭使用 FastAPI 就声称整条执行链已经异步化。

### 47. 如何应对 Prompt injection 和工具滥用？

**参考回答**

项目已有工具授权、引用校验和 SQL 限制。进一步验证时，我会加入诱导访问未授权表、伪造结果 ID、在业务文本中夹带指令等用例，并检查是否产生越权调用或泄露。安全效果需要通过具体攻击样本验证。
